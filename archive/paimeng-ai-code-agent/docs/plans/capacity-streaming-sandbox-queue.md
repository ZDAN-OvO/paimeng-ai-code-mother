# 系统容量、消息传输与沙箱排队优化计划

## 目标与范围

让系统在突发请求、慢连接、浏览器断连和进程重启时，保持明确的容量上限，并能把已接受的 Generation 收束到可解释的状态。

按以下顺序实施：**修正压测判定 → 修复准入与恢复 → 限制流式传输内存 → 接入单槽位持久构建队列 → 复跑验收。**

沿用 Next、pi-durable、Postgres、Redis 和 Docker。不新增消息中间件，不 fork SDK，不开放 bash，不引入常驻 App 开发服务器。Redis 继续只承担现有限流。

## 一、先校正证据和压测入口

以下结论作为实施依据：

- 全局并发配置为 4，同时提交时实际达到 12，准入约束确实失守。
- `/events` 完整快照重复发送造成约 33 倍流量放大，慢订阅使发送缓冲和 RSS 明显增长。
- 一万条轻量任务描述只增加约 7.4 MiB 堆；输入已持久化，不能将当前问题概括为“所有消息都只在内存里”。
- 2 MiB 合成输出确实造成过 Harness OOM，但没有定位其全部分配来源，不能断言只是某一个队列导致。

同时修正前述分析：准入缓存上限是 **32**，满时淘汰旧 token；TTL 为 **120 秒**。32 个准入失败不能直接归因于 TTL。SDK `CommittedWatch` 已限制为 **100 帧**，溢出后替换成最新快照，缺少的是字节约束。字节数也不能直接换算为真实 token 预算。

压测脚本改动：

1. 场景异常、超时、子进程退出、保护阈值触发、业务断言失败，均写入报告并以非零状态退出。
2. 每个场景记录自己创建的 App、Generation、连接和模型请求。取消或停止并确认收尾后才进入下一场景；无法清理则停止整轮，避免结果互相污染。
3. 保护阈值触发后停止发请求、终止本次模型输出，并停止本次服务；不继续尝试将中断场景计为通过。
4. 分别记录尝试数、HTTP 接受数、实际活动数、终态数和未收束数；记录 pending 字节、在途写入字节、背压次数、发送总量、RSS 和 GC 后堆。
5. 同一输出、分片、速率和并发下，对照正常读取、暂停读取、明确断开。2 MiB 输出标为异常上游场景；普通场景不声称字节数等价于 token 预算。
6. 不修改既有原始报告；在测量说明中标注场景污染、采样缺口和错误的早期解释。

**验收：** 已知的“上限 4、实际 12”断言必须失败；模拟超时/OOM 时脚本必须失败退出、保全报告并停止自有进程。

## 二、修复全局准入和模型凭证

### 2.1 用现有 authority 表直接预留容量

复用 `app_authority` 作为 Generation 容量预留，避免再维护一套平行席位事实。

- 在现有全局 advisory lock 保护的事务中，按已占用 authority 检查容量并将当前 App 置为 active；**初始化期间即占位，不再依赖 Execution 是否已登记。**
- active、draining 均占名额。过期记录先进入恢复，不因时间一到就自动从容量中消失；存在未收束 Execution 的异常记录也占位，直到完成对账。
- 增加 `reserved_generation_id` 字段，将初始化中的名额绑定到 requestId／Generation 和 epoch，支持“已占位但尚未创建 Generation/Execution”的恢复。
- 全局默认上限保持 4；超额请求返回 HTTP 429 / `42900`，附 `Retry-After: 5`，不创建新的 Generation、Execution，不解码附件为大块内存数据。
- requestId 幂等核对先于容量拒绝；重复请求不再占名额。
- 租约守护从取得 authority 后立即开始，每 5 秒续期，TTL 保持 30 秒；覆盖附件准备、目录复制、建会话、生成、验证和发布。初始化最多 30 秒，提前失败走同一收尾路径。
- 失败或发布仅能释放匹配 Generation、epoch、holder 的预留；已确认工具和容器停止、源码收尾完成后才释放。

**验收：** 12／64 个不同 App 同时请求时，第一批最多 4 个接受，其余 429；两个独立 Next 进程共同遵守同一上限。初始化任一边界失败后不遗留名额，旧 epoch 的迟到回调不能释放新名额。

### 2.2 已发出的模型凭证不被新请求挤掉

- 保留模型预检先于 Generation 创建，以及一次生成固定原模型配置的语义。
- 准入缓存改为明确拒绝超额，不淘汰仍有效的凭证；默认最多 128 个未绑定凭证，TTL 保持 120 秒。
- 凭证携带原 requestId；解析时显式检查过期。满时在预检阶段返回 429，不让已接受的请求稍后因缓存淘汰失败。
- 准入被拒、初始化失败或会话成功绑定后，显式释放未绑定凭证；已绑定会话使用持久 `app.run-model`，不再依赖 token 留在全局缓存。
- 以 Execution 标识使建会话重试幂等，避免响应丢失后创建第二个会话。
- 不通过重新读取当前模型配置来“刷新”旧凭证，避免静默换模型。

**验收：** 连续申请 64 个预检 token，前面的有效 token 不消失；第 129 个未绑定申请明确拒绝；超时、配置改变、重复建会话、Harness 重启均有确定结果。

## 三、独立于浏览器的恢复与收尾

由现有常驻 Harness 运行控制面对账循环，不新增守护服务：启动执行一次，此后每 10 秒运行；通过产品库 advisory lock 保证同时只有一个回收者，每轮最多处理 20 个 App。

- 初始化中断：找到预留并终止旧执行，封存已有源码；没有创建任何执行的预留可直接安全释放。
- editing 中断：先关闭写门并停止旧工具，再封存 Draft，写 failed/interrupted，最后释放名额。
- checking/publishing 中断：先查已提交的 Version、Delivery 和预览指针。已提交则补齐派生状态；没有提交且旧执行已停止则封存并标失败。**恢复扫描不自动接受未提交 Candidate，不重复调用模型。**
- 权限仍有效但 Next 观察者失联：建立一个内部监督入口以有限批次核对；停止无进展、无有效监督者的执行，再走恢复。不能仅因浏览器离线而取消任务。
- 对账失败保留 draining、名额和可诊断原因；不得一边释放名额一边让旧工具继续写。
- 事件监听、定时器、观察者 Promise 的异常统一进入收尾；禁止未处理拒绝使清理被跳过。

**验收：** 在占位、复制目录、模型运行、构建、发布事务前后分别终止 Next/Harness；服务恢复且基础设施可用后，60 秒内进入终态或明确的 draining 错误状态，不需访问页面触发。发布最多一次，原 Delivery 始终可访问。

## 四、给流式消息明确的内存边界

### 4.1 `/events` 发增量，重连给快照

协议升级到 13，Next 与 Harness 同步发布。

- 首次连接发送 `snapshot`，包含当前投影视图和 `revision`。
- 后续发送 `revision`：`{baseRevision, revision, changes}`。变更只包含实际变化，支持字段设置/删除、字符串追加和数组追加；不能把每次文本追加编码成整个字符串替换。
- 新增共享的纯函数负责生成与应用增量。前端或诊断消费者发现 revision 不连续时重新连接获取快照，不猜测缺失内容。
- 兼容旧快照消费者使用显式 `format=snapshot`；最多每秒发一次，仅保留最新待发状态。默认新协议使用增量，最终状态立即刷新。
- 心跳保持每秒，但连接处于背压时合并/跳过心跳。

### 4.2 统一有界写入

- Harness `/events`、`/agent-events` 使用同一有界发送器。`write()` 返回 false 后等待 drain，不能继续向 socket 写入。
- 默认每连接待发队列上限 256 KiB，单帧上限 4 MiB、单个在途帧最多一个；所有连接的待发及在途应用数据合计上限 64 MiB。超过任一上限或持续背压 5 秒，停止该订阅并要求重新同步。
- `/events` 可合并尚未发送的状态；`/agent-events` 不静默丢工具、计费和完成事件，超限断开后由 Next 按现有持久快照和 Attempt 账本对账恢复。
- 限制浏览器订阅：每会话最多 4 条，全局最多 64 条；内部 Generation 观察者独立计数，最多随 4 个活跃 Generation 各一条，不被浏览器挤占。
- Next 的 `ChunkChannel` 与输出流合并为一个按需消费的有界通道，避免数组有上限但 SDK `ReadableStream` 继续无界 enqueue。待发上限同为 256 KiB。
- 浏览器断连或通道超限后立即 detach、清空该订阅缓存；Generation 的监督、计费和收尾继续，不与浏览器 AbortSignal 共用。
- 前端收到 `data-resync` 或非正常流结束后，从现有 runtime／messages 接口恢复；运行中按最多每 2 秒一次刷新，隐藏页面暂停、网络失败指数退避至 10 秒，终态再同步一次。按消息/条目 ID 替换，避免拼接重复文本；不自动重发用户输入。
- NDJSON 解析增加 4 MiB 单行上限和 reader finally 清理；防止无换行输入无限增长。

**验收：** 文本及工具最终内容与持久 Transcript 一致；慢客户端只影响自己的视图。相同 256 KiB、单轮基线下，新增量协议每个正常订阅累计数据不超过原文 4 倍；64 个暂停订阅不能突破配置的队列字节上限，受限连接可重连恢复。

## 五、限制输入、异常输出和常驻缓存

这些是资源保护参数，不声称与模型 token 限额等价；均可配置。

- 每 Generation 最多 16 条未结算用户追加输入、累计 64 KiB 文本/元数据；附件继续引用既有对象，不把 base64 放入排队记录。计数在 App 行锁内检查；同 requestId 同内容重试先返回已有结果，不重复占额。
- Generation 仍沿用原 Deadline，排队和重挂不延长；不得自动丢弃已接受输入。结束时未处理输入按现有 unanswered 语义保留。
- 在 provider 流进入 SDK 状态前统计本次模型响应实际产生的 UTF-8 字节，默认上限 512 KiB，包含文本、思考、工具参数；超过时终止本次调用并走现有失败/草稿保留路径，不截断后当作成功，不自动重试同一异常输出。累计增量计数避免重复计算 partial/full 快照。
- 在 Harness 输入侧验证 Execution、epoch 和容量预留，防止通过透传的 `/conversations`、`/submit` 绕过正式准入；保留 Owner 检查，测试桩走显式测试环境。
- 清理 `admissionChains` 的已完成 Promise；仅在 Generation 终态、无运行任务、无订阅后回收应用级 conversation/model/workspace/web-session 缓存。空闲缓存默认最多 128 个、10 分钟；不直接删除 SDK 内部对象或持久 Transcript。

**验收：** 第 17 条待处理输入被明确拒绝，数据库和 SDK 均不多一条；容量边缘并发请求仍精确限额。异常 2 MiB 输出在积累完整内容前受控失败，原预览保留，不造成服务 OOM。连续多轮生成结束后的缓存数量有上界。

## 六、沙箱构建接入 Postgres 持久队列

这是最后一阶段，只承接当前受控构建，不扩大为任意命令执行平台。

### 数据和执行约定

新增 `build_job` 与固定的 `build_slot` 单槽位记录，使用现有 Postgres，不引入 pg-boss 或 Redis 队列依赖。

- Job 保存 App、Execution/维护操作 ID、epoch、幂等键、源码指纹、隔离构建目录引用、状态、Deadline、worker token、容器标签和有限结果摘要；不存源码、图片和完整日志正文。
- 状态为 queued → running → stopping → succeeded/failed/cancelled/expired。任务结果与清理错误分别保存。
- 对相同逻辑调用使用稳定幂等键；工具调用绑定 toolCallId，平台验收绑定已有 build Attempt，手动重建绑定维护操作。跨重启继续查询原 Job，不凭源码指纹合并不同业务调用。
- 在调用方已有的读写边界内复制源码到本 Job 独立构建目录，校验文件、配额和摘要后才入队；构建产物导回前再次核对 epoch 和源码指纹。源码改变使旧结果失效，不能覆盖新源码的预览。
- 全局最多 32 个等待任务，每 App 最多 1 个等待任务；队列满立即拒绝且清理未引用临时目录。默认等待上限 120 秒，并受原 Generation Deadline 约束。
- Harness 内一个构建执行器每秒轮询，使用短事务领取 Job 并占住固定槽位；其他 Next/Harness 进程不能直接启动构建容器。Docker 执行不持有长数据库事务。
- 槽位每 5 秒心跳、30 秒判断失联。失联先阻塞并核对容器标签、Job ID 和 worker token，确认旧容器停止后才释放；替换现有按容器创建时间清扫的逻辑。
- 崩溃后 queued Job 仍可执行；running/stopping Job 对账旧容器并收束为 interrupted/failed，不自动重复执行状态不明的构建或发布。需要重试时由现有有界 Repair/业务重试发起新 Attempt。
- 清理失败保留 stopping 和槽位；数据库不可达时不启动新容器，当前执行器终止自己拥有的任务，恢复后再对账。

### 复用与兼容

- `buildPreview`、最终验收、手动重建、历史版本的必要重建统一调用 `requestBuild(operation) → jobId`、`waitBuild(jobId)`、`cancelBuild(jobId)`。
- 只读依赖按镜像身份和模板锁文件 hash 准备一次；沿用原型验证的只读依赖挂载，Vite 临时目录独立可写。构建失败不修改共享依赖。
- 同一次构建的类型检查与打包复用容器；不同 Job 销毁后重新创建。依赖准备也占同一个槽位，安装有网络但不接触生成源码，执行生成代码时断网。
- 单容器保持 768 MiB、1 CPU、128 进程并禁用 swap；磁盘使用独立受限构建目录，源码复制和产物导出继续执行现有数量/大小校验。此阶段不开放 shell，因此不把这些校验宣称为任意 shell 的磁盘配额方案。
- 增加 transient `data-build-queue` 和可选 `buildJob` 运行态字段，显示等待／执行／停止；不新增 Generation 公共状态。排队本身不重复消耗构建 Attempt。

**验收：** 多进程从所有入口提交时，最多一个构建容器；队列满和等待超时明确失败；取消等待不建容器。执行器在建容器前后及导出前崩溃，不能遗留第二个并行执行或重复发布。React/Vue 真实构建与原型结果一致。

## 七、迁移、验证与交付

### 兼容与部署

- 仅追加迁移：authority 预留字段，以及构建 Job/槽位表和必要索引；不改已应用迁移，不新增聊天消息事实表。
- 数据库准备先于新代码；协议 13 的 Next 与 Harness 同步重启，旧协议明确拒绝，禁止静默兼容绕过门禁。
- 维护窗口先停止接受新任务并等待现有任务退出；对历史残留 active 记录执行受控对账，不直接删除记录或手工清空名额。
- 回滚代码前必须清空/收束新构建队列，确认旧容器已停止；保留追加表，不做破坏性回滚迁移。

### 必须通过的验证

1. **集成：** 12/64 请求、双 Next 进程、重复 requestId、初始化故障、token 容量与过期、所有终态释放。
2. **传输：** 快读、暂停、断连、重连、revision 缺口、超大 NDJSON、工具事件与计费幂等；断浏览器不取消 Generation。
3. **恢复：** SIGKILL Next/Harness/执行器，覆盖初始化、editing、checking、publishing 和构建 stopping；验证草稿、旧预览及单次发布。
4. **资源：** 64 个慢订阅，队列字节有界；4 个异常输出受控失败。相同隔离生产构建中，Next/Harness 各自 RSS 峰值低于 900 MiB 保护阈值，无 OOM；10 轮相同负载后 GC 堆不持续线性增长，最后 3 轮差值不超过 20 MiB。实际字节上限是硬验收，RSS 是该机器的容量验收。
5. **系统：** 真实 React/Vue 构建、共享依赖只读、多入口单容器、取消和失联回收、队列重启恢复。
6. **项目检查：** 相关 unit/integration/system/E2E 顺序运行，执行 `check:fast`、类型检查及生产构建；重置测试只使用 `_test` 数据库和 Redis DB15。

### 交付顺序

- 第一批：可信压测、原子准入、凭证容量和周期恢复；复验后再改消息协议。
- 第二批：增量视图、有界传输、前端重新同步、输入/输出与缓存限制。
- 第三批：持久构建队列、单槽位执行器和依赖共享。

每批保存原始报告及前后对照，更新现行运行/压测文档；已完成的调查结论进入项目计划归档，避免与当前实现形成两套说明。未经明确授权不提交、推送或发布。

## 默认假设

- 单机、单 Harness 写进程，允许多个 Next 进程；共享本地运行目录和 Postgres。
- 公共 Generation 超额暂时返回 429，不新增用户级的长期 Generation 等候队列。
- 浏览器离线时 Generation 继续，靠显式取消终止；恢复完整消息与状态，不承诺逐 token 精确重放。
- 所列容量参数是可配置的保守初值，实施验收不通过时报告失败并调整实现，不降低断言取得通过。
- 不同时处理计费新功能、UI 重设计、数据库迁移旧账、gVisor 或多机调度。
