# 原型 · 额度管理（积分单账本）

**这一版要回答的问题是：限时积分既然只是积分的一种（带有效期），那它该不该单独成池、单独成表、单独一个页签？**

现状是两套东西叠在一起：`credit_grant` 里 `source=monthly_quota` 已经是一种入账，但它同时又是 `credit_account.pool='quota'` 的第二套余额语义，背后再挂 5 张配额表（policy / issue / adjustment / batch / batch_item）。结果是额度管理被拆成「积分管理 / 配额管理」两个页签，配额那一页有 10 个分区：5 张统计卡、全局策略表单、单用户覆盖、策略版本表、当月调整表单回执、批量发放预览/执行/重试、批次记录、发放与待发表。

这个原型把前提换掉再看：**只有一张流水，限时积分是其中 `kind='quota'` 且带 `expires_at` 的条目。**

## 已经定下的口径

- **单位对外叫「积分」，不再出现 Credit。** 内部表名/字段名（`credit_grant`、`credit_entry` 等）这一轮不动，改不改名是后续迁移的事。1 积分仍是 ¥0.01 面额，不可兑换、不可提现。
- **「月度配额」改称「限时积分」**：会月底过期的积分。相对的「长期积分」不过期、不随账期清零。两者是同一张流水里的两种入账，不是两个池。
- **「调整月度配额」改称「发放限时积分」**：不再有 increase / decrease / target 三种意图，管理员只做一件事——输入数量，追加一条本月到期的条目。
- **发放走弹窗**：`发放限时积分` 与 `发放积分` 两个按钮都只弹一个框，填数量（带 100 / 500 / 1,000 / 5,000 快捷键）和理由，确认后账本多一条条目。没有第二步、没有预览批次。
- **结构选 A（主从账本）**（2026-11-02 结论）。B / C 留在目录里只作对照，不再推进。

## A 选型的布局约束

- 左右两栏**底边对齐**：右栏内容多长，左栏就跟多高；A 变体铺满视口，页面本身不滚动。
- 内容超出时**各自出现滚动条**：左侧用户列表一列、右侧流水一列；流水表头滚动吸顶，「流水」标题和余额区不滚。
- 左侧列表：搜索框 + `全部 / 欠款 / 待发` 三个筛选（**支持只看欠款**），底部固定「演示数据 N / 212 人」。
- 顶部摘要里的「N 人欠款」「N 人本月限时积分未发」本身就是筛选入口，点一下等于切筛选并自动选中第一个匹配的人。

## 三个变体

| key | 名字 | 结构 | 它押的判断 | 代价 |
| --- | --- | --- | --- | --- |
| `A` ✅ | 主从账本 | 左边人、右边一本流水；顶部一行全库摘要；两个发放按钮 + 账本 | 管理员来这里是**看某个人为什么是这个数**，所以流水是正文 | 全库批量操作没有主位，要挂到别处 |
| `B` | 待办收件箱 | 主区是今天要做的 5 件事（待发 / 缺费率 / 欠款 / 规则待生效 / 补结算），查人走搜索进抽屉 | 日常只有一个问题：**今天要发什么、要补什么** | 想看全局分布就得搜，不能扫表 |
| `C` | 规则 + 例外 | 只有一张表：一条规则条 + 每人一行，批量选中后底部浮条 | 额度管理本质是**规则 + 额外发放** | 单人的账本要二次进入 |

A 已选定，B / C 只在需要回顾「当时还考虑过什么」时打开。

## 三个变体都成立的前提

- 每个人只有**一个**可用额数字：`可用 = 条目之和`。没有「配额池 / 余额池 / 合计可用」三行字。
- 限时积分、长期积分、充值、消费、过期是**同一张流水**里的条目；手动发放只是其中一条。
- 扣减顺序只有一条：**先扣最先过期的**。「先配额池后余额池」这条规则不需要存在。
- 过期是**一条显式条目**（`−12` 上月剩余清零），不是隐式的月初重置；这样「为什么这个月少了 500」在账本里能直接读到。
- 「配额管理」这个页签不存在；「每月发多少」是一条规则，改规则只影响未来账期，当月要改就发限时积分。

## 模型提案

浮条右侧「模型：单账本」里有完整对照。核心字段：

```
credit_entry(user_id, kind, credits, period, expires_at, reason, operator_id, request_id, ref)
```

`kind ∈ quota | topup | grant | consume | expire`，`credits` 有符号。**限时积分 = 带 `expires_at` 的 quota 条目，长期积分 = 不带 `expires_at` 的 topup / grant 条目。**

| 旧 | 新 |
| --- | --- |
| `credit_grant` source=monthly_quota 且 pool=quota | `entry.kind='quota'` + `expires_at` |
| `credit_quota_issue`（每账期发放事实） | 就是那条 quota 条目本身 |
| `credit_quota_adjustment`（手动加/减） | 另一条 `kind='quota'` 条目 |
| `credit_quota_batch` / `_batch_item` | 同一 `request_id` 下的一组 quota 条目 |
| `credit_quota_policy` | 一条规则（保留生效账期与版本） |
| `credit_account` 两行余额快照 | 由条目推导的可用额（缓存可留，概念删掉） |

### 还没定的（原型故意没替你决定）

1. 「每月自动发放多少」还需不需要「未来账期版本」这套机制，还是全局配置 + 单人覆盖就够。
3. 透支线（近 60 天充值 × 2%，封顶 500）怎么表达：仍是配置，但不再是池的属性。
4. 批量发放的逐用户回执要不要留表：失败原因与重试范围塞进条目，还是留一张操作日志。
5. 「本月规则还没发，但管理员手动发了限时积分」这种人：原型保留「待发」状态（他还缺规则那条），没有替他决定算不算已发。

## 演示数据

- 时间固定在**北京时间 2026-11-02 15:53**，账期 `2026-11`，限时积分 `12-01 00:00` 到期。
- 全库口径（212 人 / 11 人待发 / 可用合计）照现状截图取量级；表格只渲染 12 条，页脚与列表底部都标了「演示数据」。
- 10 月的发放额固定 500：改规则**不回写**历史条目。
- 所有操作只改内存里的条目与数字，刷新即重置。发放、改规则、批量都不发请求，也不代表接口会这么设计。

## 已知限制

- 没接真实接口：`requestId` 幂等 / 失败重试只在文案里出现，没有交互。
- 账本只造了 10 月与 11 月；更早的周期没有数据。
- 「补结算」「账单与冲正」只给 toast，不展开；这块现状已有实现，不在本轮对齐范围。
- 抽屉里的流水与 A 一致，不是「最近 20 条」的真实截断。
- 批量发放（B 的「现在发」）仍按规则金额直接发，没走弹窗：它是规则发放，不是手动发放。
- 手动给「待发」用户发限时积分后，状态仍是待发——这是有意的简化，见上面第 5 条。

## 实施决策

结构已确认用 A，落地方式见 [`docs/plans/credit-ledger-unification.md`](../../../plans/credit-ledger-unification.md)。计划对原型的一处细节做了收敛，**以计划为准**：

- 过期行是**真实条目**（`kind='expire'`，账期边界写一条负行）。写入靠懒触发 + CLI 兜底；万一没跑，读模型会扣掉未写出的余量，所以页面上不会多算。
- 「已发 / 待发」只看本期有没有规则发放的条目，不看金额；规则算出 0 时也留一条 0 金额回执行（用户侧账单隐藏），不再单独建 issue 表。

## 看完需要你回答

1. 模型这一层同不同意：限时积分收成 `entry.kind='quota'` + `expires_at`，两池概念删掉。
2. 「每月自动发放多少」的规则编辑放在哪：表格上方一条规则条，还是独立设置页。
