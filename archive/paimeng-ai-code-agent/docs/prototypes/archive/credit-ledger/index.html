模型：限时积分只是积分的一个种类

现在的代码里，配额（现在叫「限时积分」）不是积分的一种，而是积分之外的第二套东西：「两池」+ 5 张配额表。 这就是页面看不懂的根：同一笔积分要分池解释、分表追溯、分状态展示。

现状（代码里的表）

  • credit_grant入账唯一入口，source 区分 purchase / admin_grant / monthly_quota
  • credit_account每用户每池一行的余额快照，pool = quota | balance
  • credit_quota_policy每月限时积分规则，按账期追加版本
  • credit_quota_issue每用户每账期的发放事实，0 积分也写一行
  • credit_quota_adjustment当月手动加/减限时积分
  • credit_quota_batch / _batch_item批量发放的预览与逐用户回执

于是同一个人要同时说清：基础 / 调整 / 已用 / 剩余 / 余额池 / 合计可用 / 发放状态 / 策略来源 / 版本。 页面上的「配额管理」就成了 10 个分区。

提案（一张流水）

credit_entry
  user_id      bigint
  kind         quota | topup | grant | consume | expire
  credits      bigint        -- 有符号
  period       'YYYY-MM'     -- 只有 quota / expire 有
  expires_at   timestamp     -- 只有 quota 有：这就是「限时积分」
  reason       text
  operator_id  bigint
  request_id   text          -- 幂等 / 一次批量操作的分组
  ref          text          -- 账单、支付单、原条目
  • 可用额 = 条目之和。没有池，没有「合计可用」这第二个数。
  • 扣减先扣最先过期的。「先配额池后余额池」这条规则消失，只剩一条。
  • 限时积分 = 带 expires_at 的 quota 条目；长期积分 = 不带 expires_at 的 topup / grant 条目。两者不建两张表。
  • 过期是一条显式条目，把上期剩余清零，不是隐式重置。
  • 手动发放、批量发放都只是生成条目，不再各自建表。

字段对照

旧新
credit_grant source=monthly_quota，pool=quotaentry.kind='quota' + expires_at
credit_quota_issue（发放事实）就是那条 quota 条目本身
credit_quota_adjustment（手动加/减）另一条 kind='quota' 条目
credit_quota_batch / _batch_item同一个 request_id 下的一组 quota 条目
credit_quota_policy一条规则（保留生效账期与版本）
credit_account 两行快照由条目推导的可用额（缓存可留，但不再是概念）

还没定的

  • 过期要不要落成条目：落条目能回答「为什么这个月少了 500」，代价是账期边界要有一次写入（可懒触发）。
  • 「每月默认额度」还需不需要「未来账期版本」这套机制，还是全局配置 + 单人覆盖就够。
  • 透支线（2% 近 60 天购买，封顶 500）怎么表达：还是配置，但不再是「池」的属性。
  • 批量发放的逐用户回执要不要留表：失败原因、重试范围，塞进条目还是留一张操作日志。

改「每月自动发放的限时积分」

这是一条规则，不是一次发放。保存只影响从这里选的账期开始，不改已发的月份。

当月要改某个人，用「发放限时积分」追加一条条目——规则不追溯。
