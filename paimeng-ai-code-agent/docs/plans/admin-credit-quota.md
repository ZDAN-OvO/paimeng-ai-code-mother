# 额度管理：Credit 管理与配额管理

状态：需求已记录，计划待实施。用户明确要求消除重复的补结算区域、支持管理员管理月度配额发放与单用户配额、查看所有用户的配额和 Credit。本轮只编写计划，不修改产品代码或业务数据。

## 目标与范围

Admin 打开「额度管理」，在「Credit 管理」页签分页查看全用户资金情况、按账号/用户名/用户 ID 找到目标用户、发放余额并查账冲正；在「配额管理」页签管理每月配额策略、执行当月发放/补发和调整单用户配额。补结算仅在 Credit 管理中保留一个按需打开的工具入口，不再跟随两个页签重复出现。

配额池与余额池都以 Credit 计量。产品文案明确区分「每月配额」「配额池剩余」「余额池 Credit」「合计可用」，避免让人以为配额与 Credit 是两种不同货币。原有先扣配额、后扣余额、配额按北京自然月失效不结转、余额不随月重置的规则继续有效。

本计划统一维护额度管理导航、Credit 管理/配额管理两个主页签、用户搜索选择和布局调整，以及全用户总览与管理员配额操作；原 TODO 清单已合并并废弃，不再单独维护。模型身份与费率管理另见 [provider-model-billing](provider-model-billing.md)，两项重构可独立推进；都改到 billing 共享契约和运维文档时顺序整合，避免互相覆盖。

- [billing-manager.tsx](../../src/components/billing/billing-manager.tsx) 目前只有「发放 Credit」「用户用量与冲正」两个页签；发放表单明确排除了 `monthly_quota`。
- [quota.ts](../../src/server/billing/quota.ts) 已有按北京自然月每用户 500 Credit 的惰性发放、并发幂等和批量补发；批量入口是 [billing-quota.ts](../../scripts/ops/billing-quota.ts)。目前没有常驻月度定时器。
- [admin.ts](../../src/server/billing/admin.ts) 拒绝管理员通过普通余额发放入口手工发月度配额；用户用量查询仅支持指定用户，没有全用户资金总览。
- [010 迁移](../../migrations/010_credit_grant_account.sql) 限制 grant 必须为正数、每用户每月只有一条基础月度 grant；当前配额重算仅识别月度 grant。因此不能直接复用「购买/补偿」入口补配额，也不能只改 `credit_account` 的余额来完成管理。

## 页面结构

沿用现有管理页视觉与交互体系，以清楚执行管理任务为主。本轮不更换全站主题。

顶部菜单「计费管理」改名为「额度管理」，继续使用 `/admin/billing` 路由。「额度」在这里作为两个管理面的菜单统称；详细金额仍明确标注配额池和余额池，计量单位都是 Credit。

仅保留两个主页签，对应用户最新要求，不再展开成五个平级页签：

| 页签 | 主要内容 | 关键动作 |
| --- | --- | --- |
| Credit 管理（默认，替代原「发放 Credit」） | 全用户配额/余额总览；用户详情中的余额发放、账单与冲正；补结算工具入口 | 搜索/筛选、选择用户、购买/补偿入账、查明细与冲正 |
| 配额管理（替代原「用户用量与冲正」） | 月度默认与用户覆盖策略、当月配额用户列表、发放状态与批次记录、单用户配额调整 | 设置未来标准、预览/确认当月发放、重试失败项、调整用户当月剩余 |

这不是仅把旧「用户用量与冲正」面板换标题：旧账单/冲正功能归并进 Credit 管理，第二个页签实际提供新的配额管理能力。用户总览、余额发放、用户账单均为 Credit 管理内部的列表/详情动作，不再增加主页签。

「补结算」作为 Credit 管理内的单一工具按钮，按需打开独立抽屉；配额管理不显示它，页签外不挂常驻补结算表格。现有功能没有完整的余额核对界面，入口暂称「补结算」，核对 CLI 保留。

全部页签与工具请求都在 Admin 权限内，不能让 `ReconcilePanel` 留在权限壳外先发请求。浏览或切换页签不运行补结算写操作。Admin 自己的 Credit 额度条不作为全用户统计；若保留，明确标注为本人余额并与管理数据分开。

### 用户总览与详情

所有未删除用户均可查询，包括管理员；没有任何 Credit 账户/发放记录的用户也在列表中。后端分页，默认每页 20，按账号/用户名模糊、完整 ID 精确搜索，支持配额待发、欠款、零可用筛选及按余额排序。筛选、排序、统计都在服务端执行，不能只处理当前页。

列表和详情的最低信息：

| 信息组 | 字段 |
| --- | --- |
| 用户身份 | `userAccount`（账号）、`userName`（用户名）、用户 ID；用户名为空有明确占位 |
| 月度规则 | 当前账期、该用户当月基础配额标准、来源为全局默认还是用户覆盖、下次生效策略 |
| 当月配额 | 基础已发金额、当月调整净额、已使用净额、当前有效剩余、到期时间 |
| 余额池 | 当前余额，可为负；累计购买、累计管理员补偿在用户详情展开 |
| 合计与欠款 | 合计可用 = 当前有效配额剩余 + 余额池；欠款额 = max(0, -余额池)，透支线独立显示，不加进可用额 |
| 状态与记录 | 本月待发/已发/零配额、数据时点、发放/调整历史与操作者；余额快照异常单独提示 |

总览可展示符合当前筛选范围的用户数、待发人数、配额剩余总量、余额池净额、欠款人数与欠款总额；每项标明范围，不能拿当前页合计冒充全库统计。余额净额与欠款额分别计算，防止负数被正数掩盖。

从总览进入详情、发放或调整时传递用户 ID，界面展示账号 + 用户名 + ID 供核对。已有两个用户输入框也改为可搜索选择，下拉候选明确展示 `userAccount`（账号）+ `userName`（用户名）+ 用户 ID；完整 ID 直接粘贴也能找到并选中用户。选中后展示可辨身份，提交仍为用户 ID。若扩展关键词搜索，服务端须支持账号/用户名的 OR 匹配，不能同时传两个现有 AND 条件导致搜不到用户。

窄屏保留身份、两池余额与操作入口；明细按信息组展开，表格可横向滚动，页面本身不溢出。表单按用户选择、金额/来源、备注和确认组织，不强塞一行。沿用 antd 的 Form 直接控件绑定和键盘可达要求。

## 管理行为与拟采用规则

以下具体生效规则为本计划建议，尚未视为用户已确认的收费政策；实施前确认后固定到契约与测试。

### 每月发多少：配额策略

- 支持全局默认月度配额和按用户设置覆盖金额；清除覆盖后恢复全局默认。沿用 500 作为迁移后的初始默认值，不自动改已有用户余额。
- 金额为非负整数，允许 0 表示该用户或策略生效范围不发基础配额。必须区分「没有覆盖，继承默认」与「覆盖为 0」。单笔/每月上限由共享契约校验，实施前确定，不默默沿用购买上限。
- 策略带生效账期与版本记录，建议从下个月或指定未来月生效；不回改已结束月份，不因修改默认值覆盖已发放的当前月。
- 页面显示当前与未来生效规则，保存前给出受影响范围及是否被用户覆盖。新增、替换尚未生效策略也留可追溯版本；并发保存使用版本校验，冲突返回 409。
- 原固定 500/月属于 [ADR-0004](../adr/0004-credit-billing.md) 的现行决策。本计划实施后允许配置属于业务规则扩展，需记录新决策，不能只改常量并让旧文档继续声称固定 500。

### 当月怎么发：基础配额发放

- 所有发放入口统一解析当月有效策略，按 `(userId, period)` 幂等发基础配额：注册、本人摘要、新生成准入、管理员单用户补发、管理员批量发放与 CLI 使用同一逻辑。
- 每用户每月固定一次基础发放标准与策略版本，之后调整走独立调整记录；已发 500、用掉 200 时点「补发」不能重新恢复到 500。
- 支持当月单用户与批量「预览 → 确认发放」，展示目标账期、范围、人数、各金额与合计、已发跳过项、失败原因。默认不允许给已结束月份补发可用配额，也不提前把未来月配额计入当前余额。
- 批量执行有明确范围、上限、批次 ID 和进度，目标用户及策略版本固定；大范围分批执行，失败可按原批次重试，不能只处理第一页却提示「全用户已发」。策略或账期在确认前改变则拒绝旧预览，重新计算。
- 批量与用户惰性触发并发时只发一次；部分失败展示逐用户结果，已成功项重试跳过。新注册用户不混进旧批次，仍可由注册路径获得当月配额。
- 首期继续使用惰性触发 + 管理员批量入口 + 可由外部定时任务调用的 CLI；页面如实显示执行记录，不宣称已有每月定时调度。若要求月初主动发完全库，再单独接入并验证调度运行状态。

### 单个用户当月怎么调：配额调整

- 支持增加/扣回当月尚未使用的配额，或输入目标剩余金额由服务端在锁内计算差额。说明本次改的是「当月剩余」而非下个月标准。
- 确认时展示用户三项身份、当前剩余、调整差额、调整后剩余、到期时间；理由必填，记录操作者、请求幂等键、前后值和时间。
- 调整前先确保基础月度发放状态，所有余额锁顺序与结算一致；扣回不得超过当前可用配额，不允许配额池变负，也不改写已发生的消费。
- 新增配额同样月底失效，不计入购买额或透支基数。用户后续读取摘要、CLI 补发、核对重建不能把调整抹掉或重新补满。
- 已结束月份只读；若当时少给配额，需要显式给当前月追加，不能让过期配额复活。退还旧账期消费仍按原有规则归到旧账期。
- 给余额池加钱继续走独立的购买/补偿入口；调整配额不能绕过来源约束写进余额池。

## 账本、数据与查询设计

### 追加的数据

拟新增以下记录，具体字段在实施时由 SQL 与共享契约统一定义：

1. **月度配额策略版本**：全局或用户范围、生效月份、金额、继承/覆盖规则、操作者与版本信息。新策略不重写已发月份。
2. **用户账期基础发放记录**：每用户每月唯一，固定本期基础标准、策略版本与实际发放状态，关联原 `monthly_quota` grant。金额 0 也记状态，不伪造零金额 grant、不让惰性逻辑退回默认 500。
3. **当月配额调整记录**：有账期的有符号差额、原因、操作者、requestId、前后值，只追加。`credit_entry` 属于 Generation 扣费，不给管理员调整伪造 Generation。
4. **发放批次与结果**：固定的执行范围/策略、进度、逐用户回执、失败信息与幂等标识；有限批次和重试即可，不引入通用工作流引擎。

保留原 grant、charge、entry，不回改已应用迁移。已有月度 grant 可关联为对应账期基础发放事实；不能只因当前标准为 500 就把所有旧发放记录改成 500。

当前配额真值公式统一扩展为：

```text
当前有效配额 = max(0, 当期基础已发 + 当期调整净额 - 当期配额消费净额)
合计可用 = 当前有效配额 + 余额池余额
```

本人摘要、Admin 总览/详情、准入、结算分池、运行期透支评估、audit/rebuild、CLI 都用同一口径。调整和结算竞争同一用户的锁，禁止直接设置余额快照却不写事实。跨期失效、退款恢复上限和调整扣回边界要在实现中用同一公式验证，不新增一套只供页面使用的金额算法。

### 总览查询必须只读

- 总览和详情浏览不逐用户调用 `ensureCurrentPeriod`，否则打开管理页就给全库发钱，也会形成 N+1 查询。发放是显式动作，已有本人摘要惰性发放规则保留。
- 使用用户表左连当期基础发放、按用户/账期预聚合的调整和配额分录、余额池聚合；购买与补偿分别汇总，避免多张明细直接 join 造成金额倍增。
- 跨月时不把 `credit_account` 中上月遗留的配额快照当作当前可用。无当期基础发放时显示「待发」、基础已发为 0；若存在合法当期调整，按当期事实计算剩余，不制造“预计可领”余额。
- 读取采用统一账期与数据时点，分页查询与统计使用一致快照；按总览筛选统计，而不是客户端累加当前页。不同页是不同读取时点时明确显示，刷新更新。
- 既有余额快照可作为加速与核对对象，但发现与事实不符时不静默写库；金额使用明确的有效账期口径，并展示异常。性能验证包含查询数量和预聚合索引，不逐行拉账单。

### 模块与请求

后端按配额策略、发放、调整、总览读模型划分职责，统一封装在 billing 内；前端不自行重算配额。新增 Admin-only 的分页总览、策略读写、发放预览/执行、调整与记录查询；沿用业务信封、来源校验、服务端用户检查、BusinessError、整数金额和字符串 ID。

普通用户不得列全用户余额、查看他人策略或执行任何写操作。重复 requestId 的相同意图返回原回执；不同载荷复用同一键必须拒绝。发放、调整、策略修改都有审计记录，余额读接口不携带写入副作用。

## 实施顺序与验收

| 阶段 | 工作 | 验收 |
| --- | --- | --- |
| C1 信息架构与总览 | 额度管理导航、Credit 管理/配额管理两个主页签、单一补结算工具、全用户分页读模型、用户搜索与详情跳转 | 仅两个主页签，补结算表格不常驻页签外；默认能看全用户而非必须先填 ID；旧账单冲正可从 Credit 管理访问；浏览无账本写入；未开户用户可见 |
| C2 配额策略与基础发放 | 策略版本、用户覆盖、0 配额状态、统一惰性入口和 CLI、旧数据迁移 | 继承与覆盖正确，次月策略不改当前月；0 不会补成 500；所有入口并发同月仅一笔基础发放 |
| C3 当月单用户调整 | 正负调整事实、理由、幂等回执、统一余额重算 | 增加、扣回、目标剩余可核对；不能扣成负配额；刷新/摘要/重建不抹掉调整；并发结算不丢钱 |
| C4 管理员月度发放 | 单用户/批量预览、执行、进度、失败重试及操作记录 | 页数/批次边界完整；确认前策略或跨月变更被拒；部分失败重跑不重复发，不能从历史月复活额度 |
| C5 回归与证据 | 两池收费、冲正、过期、模型费率计划整合、权限、窄屏与功能证据 | 下面的关键场景有真实账本与页面证据，文档说明与实现一致 |

关键验收旅程：

1. 全用户总览至少跨两页，含正常余额、负余额、无当月发放、无账户记录的用户；按三项身份搜索；分页与全范围统计可独立核对。
2. 打开/切换/刷新总览与用户详情，grant、adjustment、entry 数量保持不变；跨月不显示过期配额。
3. Admin 修改未来月全局标准，给一人设覆盖、一人设 0；受控跨月后，默认用户、覆盖用户、0 用户分别得到正确结果。已有当前月消费不被重填。
4. 预览当月待发，确认执行，出现逐用户回执；模拟部分失败后重试，原成功项不重复发；与本人摘要/准入并发仍只发一次。
5. 用户当前基础发 500、已用 200，剩余 300；Admin 增加 100 后剩余 400，扣回 50 后为 350；刷新、本人摘要、audit/rebuild 后仍为 350，历史基础 grant 不变。
6. 超额扣回、理由为空、同键异载荷、旧版本保存、非管理员写操作都明确拒绝，不改变账户。
7. 当月调整在下月失效；对旧账期退款不会恢复本月配额，余额池购买/补偿与透支线不受配额调整污染。
8. 菜单显示「额度管理」，主页签仅「Credit 管理」「配额管理」；从总览选中用户进入余额发放、账单冲正，身份保持；补结算仅通过 Credit 管理工具入口打开一次，配额管理和页签外均不重复显示，保留原重试幂等逻辑。

验证分层沿用 [tests/AGENTS.md](../../tests/AGENTS.md)：策略解析和账期计算用 unit；真库、并发、迁移和批次用 integration，严格使用 `_test`；可见行为用 Playwright 和本机 `verify-paimeng-agent` 技能。证据包含初始状态、提交、中间状态、回执、刷新复核与必要 SQL，不能用接口桩或通过总数替代。

## 待确认的业务边界

实施前需要确认以下建议；这不影响先记录需求和拆分工作：

- 月度策略默认从下月生效，当月变更使用独立调整；不支持追溯修改过去月份。
- 单用户配额管理包含设置未来标准和当月增加/扣回/设置目标剩余；扣回仅限未使用部分。
- 首期管理定时发放的策略与记录，但保留现有惰性发放和外部调度入口；如需应用内自动月初批量任务，应额外确认其部署方式。
- 月度标准和单次配额调整的金额上限，在共享契约中明确定义后实施。
