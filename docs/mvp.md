# Paimeng MVP

本文件是范围、决策与里程碑的记录。架构与模块边界以 [architecture.md](architecture.md) 为准；两者冲突时先改本文件的范围结论，再同步架构文档。

记录时间：2026-11-06。来源是一轮逐问确认的架构讨论，每个结论都由产品负责人选定。

## 1. 一句话

开源版的 v0：描述一句需求，得到一个能跑、能改、能发布的 Next.js 应用。

成功标准不是生成了一段代码，而是**一个没写过代码的人，从 clone 仓库到拿到一个可访问的网址，全程不需要离开浏览器**。

## 3. 明确不做

多人协作与邀请、Figma 导入、Vercel 一键部署、GitHub PR 导出、数据连接向导、计费与额度、组件市场、移动端 App、公开模板画廊、用户发布模板。

这些每一项都能独立成一个大功能，加起来正好是 v0 剩下的部分。MVP 只做主干闭环。

## 4. 决策记录

### 4.1 范围与形态

| 编号 | 问题                  | 结论                                               | 理由                                                |
| ---- | --------------------- | -------------------------------------------------- | --------------------------------------------------- |
| Q1   | 「v0 的 60%」怎么定义 | 换成 13 条可演示路径，按工程量而非功能面计数       | 功能面永远数不满，可演示路径无法糊弄                |
| Q8   | 验收口径              | 不出现百分比，逐条靠 PR 点亮                       | 同上                                                |
| Q6   | 前端复刻到什么程度    | 结构与交互对齐 v0，视觉用 shadcn 默认              | 旧库是 Ant Design，前端等于重写；像素级复刻收益低   |
| Q9   | Design mode 做到哪层  | 只做点选元素并生成对话输入，不做样式面板与实时写回 | DOM 到源码已是最贵的一步，实时写回再贵一个量级      |
| Q10  | 发布形态              | 容器托管，不用静态导出                             | full-stack 项目的 API route 与 SSR 在静态导出下失效 |
| Q11  | 账号模型              | 单用户本地优先，所有表带 `user_id`                 | clone 下来就能跑；注册墙会杀死开源版的第一体验      |
| Q12  | 数据模型              | Project → Chat → Version 三层，发布挂在 Project    | 与 v0 同构；只做 Chat 会在第二次迭代时被迫改表      |
| Q13  | 模型选择器            | 做，选择随 Chat 保存                               | 成本低、显眼，且能对比本地网关与线上 provider       |
| Q26  | 模板指什么            | 只做内置起始模板，不做用户发布与画廊               | 画廊是社区产品面；起始模板直接决定生成质量          |

### 4.2 仓库与迁移

| 编号 | 问题               | 结论                                                     | 理由                                               |
| ---- | ------------------ | -------------------------------------------------------- | -------------------------------------------------- |
| Q2   | 新代码放哪         | 同一仓库，新代码直接落仓库根                             | 历史、CI、issue 留在原处；不另起仓库制造死资产     |
| Q25  | 是否套一层目录     | 不套，根目录就是应用                                     | 少一层嵌套，路径与命令都短                         |
| Q3   | 旧代码带走什么     | 零代码复用，只带本地网关配置、Postgres 实例与踩坑清单    | 旧 schema 压着计费与配额，带进来就变成计费系统复刻 |
| Q7   | 旧库与 PR 怎么处理 | 归档进 `archive/`，关闭全部开放 PR，保留分支与提交       | 关闭可逆，删分支不可逆；旧结论仍有参考价值         |
| Q31  | 何时执行           | 立即执行，文档、归档、关 PR 一次做完                     | 旧目录的依赖与 CI 会持续抢注意力                   |
| Q32  | 仓库改名吗         | 保持 `paimeng-ai-code-mother`，README 说明重构与目录作用 | 改名随时可做，先把手上的事做完                     |

### 4.3 Agent 运行时

| 编号 | 问题               | 结论                                                 | 理由                                               |
| ---- | ------------------ | ---------------------------------------------------- | -------------------------------------------------- |
| Q14  | 循环用什么搭       | `ToolLoopAgent` 加自定义 `SandboxSession`            | 循环、多步、工具、流式都是 SDK 已有能力            |
| Q15  | 进程崩了怎么办     | 不做持久化执行，消息每步落库，中断即失败可重试       | Workflow DevKit 是上一轮返工的来源；重试成本可接受 |
| Q16  | 预览怎么送到浏览器 | 沙箱内 `next dev`，宿主机反向代理，含 HMR WebSocket  | 迭代必须改完即见，构建等待不可接受                 |
| Q17  | 版本怎么存         | 每条助手消息后快照源码树到宿主机，diff 比对两棵树    | 文件级 diff 与回滚不需要 git 的推送与冲突语义      |
| Q18  | 数据层             | PostgreSQL 加 Drizzle，编号 SQL 迁移                 | 沙箱已强制依赖 Docker，多一个容器不增加门槛        |
| Q19  | 模型怎么配         | `config/providers.json` 加环境变量密钥，密钥永不入库 | 开源项目的密钥不该进数据库或镜像                   |
| Q20  | 发布流水线         | `.next/standalone` 产物加通用 runner 镜像            | 不为每个应用构建镜像，也不需要本地 registry        |

### 4.4 技能系统

| 编号 | 问题               | 结论                                                                                 | 理由                                                  |
| ---- | ------------------ | ------------------------------------------------------------------------------------ | ----------------------------------------------------- |
| Q4   | skill 是什么       | 与 Claude Code 同构：带 frontmatter 的目录，含 `SKILL.md`、`references/`、`scripts/` | 架构轻、可靠，且已有成熟形态可参照                    |
| Q4b  | 谁做路由           | 生成模型自己：描述进 system prompt，正文用 `load_skill` 按需加载                     | 少一次调用，模型能看到对话细节                        |
| Q4c  | 谁可以写技能       | 内置技能加用户自建与导入                                                             | 用户扩展是产品的一部分                                |
| Q4d  | 用户技能存哪       | 磁盘为真源，数据库只存索引                                                           | 技能本质是文件树，可直接挂进沙箱                      |
| Q4e  | 脚本信任边界       | 与生成应用同沙箱，目录只读挂载，导入时显式信任                                       | 同沙箱爆炸半径是用户自己的数据；独立容器在 MVP 不划算 |
| Q21  | 帮用户做技能       | 内置 `skill-creator`，通过受控 `create_skill` 工具落盘                               | 复用同一套机制，不另开编辑路径                        |
| Q22  | 技能多了怎么办     | 描述全量列出，不设上限                                                               | 一行一条，五十条约一千多 token                        |
| Q23  | DOM 到源码怎么映射 | 读 React fiber 上的 `_debugSource`                                                   | 开发构建自带，不依赖构建期插件与源码映射              |

### 4.5 沙箱、发布与运行

| 编号 | 问题         | 结论                                              | 理由                                               |

| Q5   | 沙箱怎么实现 | 实现 AI SDK 的 `SandboxSession`，后端本地 Docker  | 接口一致，后接云沙箱只是换实现；旧库已验证隔离参数 |

## 5. 技术底座

- Next.js App Router + React + TypeScript，代码在仓库根。
- Tailwind CSS + shadcn/ui。
- Vercel AI SDK 7，`ToolLoopAgent`，单进程循环，无 durable execution。
- PostgreSQL + Drizzle，编号 SQL 迁移。
- Docker：开发沙箱与发布 runner。
- 单实例部署。

## 6. 里程碑

每个里程碑以「能演示」为退出条件，不以代码写完为准。

| 里程碑                | 内容                                                               | 退出条件                                                  |
| --------------------- | ------------------------------------------------------------------ | --------------------------------------------------------- |
| M0 骨架               | Next.js、Tailwind 与 shadcn 基础、Drizzle 与首条迁移、健康检查、CI | `docker compose up` 后 `/api/health` 返回应用与数据库就绪 |
| M1 沙箱与预览         | Docker `SandboxSession`、容器生命周期、`next dev` 反向代理         | 一个模板项目在预览里打开并热更新                          |
| M2 生成闭环           | `ToolLoopAgent`、文件工具、流式、消息持久化                        | 一句话生成项目，在预览里看到页面，并继续改一轮            |
| M3 代码面板与版本     | 文件树、只读查看、快照、diff、回滚                                 | 改两轮后能看 diff，回滚后预览回到旧版本且历史追加一条     |
| M4 技能系统           | 技能加载、`load_skill`、`skill-creator`、导入与信任                | 用户创建一个技能，下一轮对话里被用上                      |
| M5 发布               | 构建产物、runner 容器、`/p/<deployKey>`                            | 发布后换浏览器打开地址仍可访问；回滚后重新发布生效        |
| M6 Design mode 与截图 | fiber 定位、点选生成输入、截图上传                                 | 点预览元素自动填入一条指向该组件的对话                    |
| M7 补齐               | 搜索、内置模板、环境变量面板                                       | 13 条全部可演示                                           |

## 7. 验收与证据

- 每个功能 PR 附浏览器录屏（GIF 嵌入正文）与必要的截图。
- 数据库行、沙箱输出、日志随附，但不能替代可见证据。
- 没有可见界面的改动，在 PR 里说明，不用终端输出冒充。
- 验收以本文件第 2 节的演示路径为准，不以单元测试通过为准。

## 8. 风险与未决

- `experimental_sandbox` 的确切接入点要在 M1 实测：挂在 agent 设置上，还是工具执行上下文里。
- `next dev` 反代要处理绝对路径、HMR WebSocket 与子路径，先做 spike。
- standalone 产物在 runner 里对静态资源与 API route 是否都成立，M5 验证。
- 快照体积随项目增长，需要保留策略。
- 技能描述不设上限，技能很多时可能注意力稀释；先观察，不提前加预筛。
- 用户技能脚本与生成应用同沙箱，信任模型是 MVP 的折中，M4 需要把导入清单做成可读的确认页。
