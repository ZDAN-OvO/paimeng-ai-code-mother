# Paimeng MVP

本文件是范围、决策与里程碑的记录。架构与模块边界以 [architecture.md](architecture.md) 为准；两者冲突时先改本文件的范围结论，再同步架构文档。

初版记录时间：2026-11-06；最近更新：2026-11-07。来源为逐问确认的架构讨论与后续工具、Skill、Agent 循环规划。本文记录产品决策，不作为功能已实现的证明。

## 1. 一句话

开源版的 v0：描述一句需求，得到一个能跑、能改、能发布的 Next.js 应用。

成功标准不是生成了一段代码，而是**一个没写过代码的人，从 clone 仓库到拿到一个可访问的网址，全程不需要离开浏览器**。

### 2.1 Agent 生成流程的补充验收

保留上面的 13 条产品路径；以下是 M2／M4 对应功能的必要验收，不另起一套产品范围。详细工具边界与循环见架构第 6、7 节。

| 能力            | 可演示或可复核路径                                                                                                                  | 里程碑 |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------- | ------ |
| 八项基础工具    | 覆盖 Read、Write、Edit、Glob、Grep、Move、Delete、Bash；移动、复制与删除使用专用工具，在 Sandbox 中真实改变项目                     | M2     |
| Todo            | 多步骤请求显示任务清单与当前进度，执行时更新；失败或取消不把剩余项假报完成                                                          | M2     |
| Plan            | 用户要求先规划时只读分析并展示方案；批准后才允许实施，要求修改返回规划，拒绝则停止                                                  | M2     |
| 规划权限        | 等待审批前后刷新仍能看到方案与决定；Plan 中写入、删除和通用 Shell 被执行器拒绝，改动方案不能复用旧批准                              | M2     |
| 验证与修复      | 可修复的构建错误由 CI 返回主 Agent，修复后重跑检查；旧修订的通过结果不能用于新改动                                                  | M2     |
| Review subagent | 大改动触发 code review 并被打回、修复后通过；交付前调用 completion review，缺失项返回主 Agent；界面显示审查轮次与打回理由           | M2     |
| 完成判定与熔断  | 当前修订没有 CI 通过记录时拒绝成功状态；未经完成审查的成功轮次有标记；达到预算或用户取消后保留工作并如实显示，Todo 勾完不能绕过检查 | M2     |
| 最小 Skill 加载 | description 常驻，正文与 references 按需进入工具结果；首批设计、框架、组件与诊断规范参与生成                                        | M2     |
| 完整 Skill 管理 | 创建、导入、信任与使用 User skill；来源同名不静默覆盖，未信任脚本被受控执行入口拒绝                                                 | M4     |

生成项目的设计验收还需检查视觉层级、主题一致性、响应式与主要交互。Paimeng 工作台使用默认 shadcn，不限制生成项目采用自己的视觉方向。浏览器录屏是评审证据，不代表产品已内置浏览器自动验证。

## 3. 明确不做

多人协作与邀请、Figma 导入、Vercel 一键部署、GitHub 同步及 PR 导出、数据连接向导、计费与额度、组件市场、移动端 App、公开模板画廊、用户发布模板。

当前也不建设动态 ToolSearch、独立任务管理平台、通用制品平台或图片生成服务。Todo 与 Plan 属于 MVP 主流程，不因排除任务平台而删减。

真实浏览器自动化尚未确认，当前只承诺 Q24 的 HTTP 正文抓取与搜索。它不属于已承诺的自动验证能力，也不视为永久否决；确认范围之前不加载 `browser-validation`。

MVP 聚焦可演示的生成、修改、验证与发布主干，不复制 v0 的全部服务清单。

## 4. 决策记录

### 4.1 范围与形态

| 编号 | 问题                  | 结论                                                            | 理由                                                   |
| ---- | --------------------- | --------------------------------------------------------------- | ------------------------------------------------------ |
| Q1   | 「v0 的 60%」怎么定义 | 换成 13 条可演示路径，按工程量而非功能面计数                    | 功能面永远数不满，可演示路径无法糊弄                   |
| Q8   | 验收口径              | 不出现百分比，逐条靠 PR 点亮                                    | 同上                                                   |
| Q6   | 前端复刻到什么程度    | 工作台结构与交互对齐 v0，视觉用 shadcn 默认；生成项目按需求设计 | 区分工作台与生成项目，不把组件默认样式当作设计策略     |
| Q9   | Design mode 做到哪层  | 只做点选元素并生成对话输入，不做样式面板与实时写回              | DOM 到源码已是最贵的一步，实时写回再贵一个量级         |
| Q10  | 发布形态              | 容器托管，不用静态导出                                          | full-stack 项目的 API route 与 SSR 在静态导出下失效    |
| Q11  | 账号模型              | 单用户本地优先，所有表带 `user_id`                              | clone 下来就能跑；注册墙会杀死开源版的第一体验         |
| Q12  | 数据模型              | Project → Chat → Version 三层，发布挂在 Project                 | 区分产品、对话线与源码历史，不以 v0 API 资源模型为契约 |
| Q13  | 模型选择器            | 做，选择随 Chat 保存                                            | 成本低、显眼，且能对比本地网关与线上 provider          |
| Q26  | 模板指什么            | 只做内置起始模板，不做用户发布与画廊                            | 画廊是社区产品面；起始模板直接决定生成质量             |

### 4.6 2026-11-07：Loop、工具与 Skill 规划收敛

以当时的 Loop 讨论与工具、Skill 规划为依据，把已定内容同步为当前契约。讨论页已于 2026-11-09 删除；本表是当日记录，其中审查形态与工具名已被 4.7 取代。

| 主题              | 当前结论                                                                        | 理由或限制                                            |
| ----------------- | ------------------------------------------------------------------------------- | ----------------------------------------------------- |
| Agent 形态        | 单主 `ToolLoopAgent`，模型自己路由 Skill，检查失败返回同一 Agent                | 不增加独立路由器、Planner Agent 或验证 Agent          |
| 工具分工          | `verify_project` 执行检查；`complete_task` 核对目标与证据；宿主程序控制最终状态 | 停止调用工具、Todo 完成或达到步数上限都不等于成功     |
| 文件与项目工具    | MVP 补齐 Read、Write、Edit、Glob、Grep、Move、Delete、Bash                      | Move／Delete 有专用工具，不能仅靠 Shell 间接替代      |
| Todo              | 做可见任务清单与实际进度                                                        | 不是独立任务平台，不用勾选代替验证                    |
| Plan              | 做只读规划与批准、修改、拒绝三种审阅结果                                        | 权限由宿主控制，普通小改动不强制进入 Plan             |
| Skill 交付顺序    | M2 有最小加载与四个核心 Skill；M4 完成管理、导入、信任与制作                    | 最低生成质量不等技能管理全部建成                      |
| 系统与 Skill      | 安全、质量底线与完成条件常驻；领域知识按需加载                                  | Skill 不扩大权限，也不保证外部集成可用                |
| 版本              | 维持 Q17 与 ADR 0006，每条助手消息结束后记录 Snapshot                           | 不新增「仅代码变更产生版本」的规则，也不改为 Git 存储 |
| v0 对齐与 GitHub  | 后续仅评估，不进入当前 MVP                                                      | 与原版本方案分开，不承诺完整复制                      |
| AI 与 Agent Skill | MVP 后明确交付，第 6.1 节列明范围                                               | 服务用户生成项目，不改变 Paimeng 自身运行时           |
| 真实浏览器        | 仍未确认，维持 Q24                                                              | HTTP 抓取不能证明点击与视觉正确                       |

### 4.7 2026-11-09：review subagent 与离线调优

推翻 4.6「不增加验证 Agent」一条，其余维持。理由见对应 ADR，设计见 `architecture.md` 第 6.1 节与第 11 节。

| 主题         | 当前结论                                                                               | 理由或限制                                           |
| ------------ | -------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| 审查形态     | code review 与 completion review 是 subagent 工具，由主 Agent 判断何时调用（ADR 0013） | 自评偏松；小改动不付两次审查成本；两种审查不是一对一 |
| 宿主底线     | CI 每轮必跑，当前修订没有通过记录不能标成功；只有 CI 没有 CD（ADR 0010）               | 主 Agent 可能该审不审，确定性检查不交给模型判断      |
| Plan 与 Todo | 都是工具，由主 Agent 判断是否调用，宿主不写死流程（ADR 0011）                          | 进入 Plan 后的权限限制不变                           |
| 评测基准     | 预埋缺陷、干净项目、需要 review 的大改动三类用例，不靠 LLM 判分（ADR 0014）            | 防止调优收敛到两个模型互相认同                       |
| 调优         | 夜间离线调优，产出 PR 由用户合入；不做上线后自动调优（ADR 0015）                       | 单用户本地优先，没有汇总的线上数据                   |
| 契约         | review 的 parts 与 SSE 事件暂不写入 `api.md` 与 `schemas.ts`，M2 实现时同步            | 本次只改文档；只改一边会制造新的不一致（ADR 0009）   |

## 5. 技术底座

- Next.js App Router + React + TypeScript，代码在仓库根。
- Tailwind CSS + shadcn/ui。
- Vercel AI SDK 7，`ToolLoopAgent`，单进程循环，无 durable execution。
- PostgreSQL + Drizzle，编号 SQL 迁移。
- Docker：开发沙箱与发布 runner。
- 单实例部署。

### 6.1 MVP 后的迭代

以下 AI 与 Agent Skill 明确要做，交付批次与具体兼容版本后续细化；继续使用同一套 description 路由、正文与参考文件按需加载。

| Skill          | 交付目标                                   | 边界                                           |
| -------------- | ------------------------------------------ | ---------------------------------------------- |
| `ai-sdk`       | 生成项目中的流式输出、工具调用、结构化输出 | 不因 Paimeng 自身使用 AI SDK 而每轮加载        |
| `ai-sdk-4/5/6` | 不同主版本的用法与迁移参考                 | 识别目标项目依赖，不能混用不同版本 API         |
| `eve`          | 帮用户构建持久化、工具型、多渠道 Agent     | 具体依赖与技能规范在实现前核实                 |
| `workflow`     | 帮用户构建可暂停、恢复、重试的工作流       | 不改变 Paimeng 自身无 durable execution 的约束 |
| `chat-sdk`     | 帮用户构建多平台聊天机器人                 | 对应迭代明确平台授权、凭据与服务依赖           |

这些是生成项目的知识扩展，不是增加五个主 Agent，也不凭技能正文就宣称集成可用。

评测与夜间调优同样排在 MVP 后，按顺序：用例集成为回归门禁（拦截率、误打回率、漏审率、打回轮数、成本）→ 三 agent 与主 Agent 自查、跨家族与同家族的配对对比 → 夜间离线调优并产出 PR。设计见 `architecture.md` 第 11 节；M2 只交付用例格式与 mock 审查演示。

对齐 v0 的版本行为、用 Git 替代 Snapshot、GitHub 工作分支与自动推送及 PR 流程仅留待评估，**不是已承诺的交付**。真实浏览器范围仍单独待确认，不因本轮文档同步视为已批准。

## 7. 验收与证据

- 每个功能 PR 附浏览器录屏（GIF 嵌入正文）与必要的截图。
- 数据库行、沙箱输出、日志随附，但不能替代可见证据。
- 没有可见界面的改动，在 PR 里说明，不用终端输出冒充。
- 验收以本文件第 2 节及 2.1 节的演示路径为准，不以单元测试通过为准。
- Agent 检查结果必须对应当前源码修订；修改后的旧检查证据、模型自述与 Todo 勾选不能代替重新验证。
- CI 失败与 review 打回都要返回主 Agent 修复；当前修订没有 CI 通过记录时不得接受成功，未经完成审查的成功轮次要有标记。预算耗尽、取消和运行异常须明确呈现，不冒充通过。
- 构建或 HTTP 就绪检查不证明视觉与交互正确；通过实际浏览器操作、录屏与截图提供这部分证据，不把它写成已具备的 Agent 浏览器能力。

## 8. 风险与未决

- `experimental_sandbox` 的确切接入点要在 M1 实测：挂在 agent 设置上，还是工具执行上下文里。
- `next dev` 反代要处理绝对路径、HMR WebSocket 与子路径，先做 spike。
- standalone 产物在 runner 里对静态资源与 API route 是否都成立，M5 验证。
- 快照体积随项目增长，需要保留策略。
- 技能描述不设上限，技能很多时可能注意力稀释；先观察，不提前加预筛。
- 用户技能脚本与生成项目同 Sandbox，信任模型是 MVP 的折中，M4 需要可读的文件清单确认页；受控入口校验信任不等于来源隔离，通用 Bash 的权限必须由执行器与 Sandbox 约束。
- Plan 审批需保存方案与决定，并拦截过期批准；记录持久化不意味着进程重启后自动续跑。
- 取消、异常与预算耗尽的工作保存及恢复边界需要细化，不能放宽成功判定或悄悄改动版本触发规则。
- 真实浏览器仍待范围确认；若纳入，需另定隔离、导航与资源请求边界，不能由 HTTP 抓取充当替代。
- 主 Agent 可能把大改动判成小改动而跳过 review；宿主只兜住 CI，漏审要靠评测发现并调提示词。
- 用例绑定契约版本，契约变了不更新就会用过期用例得出错误结论；过期用例不计分，保留集定期换新。
- review 的 parts 与 SSE 事件尚未进入契约，M2 实现前需要先补 `api.md` 与 `schemas.ts`。
