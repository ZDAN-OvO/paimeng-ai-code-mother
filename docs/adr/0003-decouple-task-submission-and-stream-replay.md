# 拆分任务提交与流订阅，用事件流同步多标签页输出

Java 保证同一应用在同一时刻只运行一个生成任务。前端与 Java 之间的代码生成接口拆分为「提交任务」和「订阅任务事件流」两步，取代原有的单次 GET 请求直接拉取 SSE 流的方式。

Java 收到 Python 推送的流式内容、工具进度、构建修复状态及终态事件后，按顺序写入该任务的 Redis Stream，并实时推送给所有已订阅的页面。用户刷新页面、关闭后重开，或在另一个标签页打开正在生成的应用时，客户端接入该任务的事件流：先按顺序回放本轮已输出的内容，再无缝接收后续实时推送，使所有页面在流式输出期间保持同等展示状态。

并发提交按以下规则处理：重复提交同一次请求时，Java 返回已有任务；如果同一应用已在生成时收到另一条不同指令，Java 拒绝新建任务并返回当前进行中的任务信息，前端提示「该应用正在生成」、保留后发页面的输入框内容不清空，并自动接上当前任务的事件流。

Redis Stream 用于实时同步和断线回放，任务结束后按设定的过期时间清理。Java PostgreSQL 持久化任务状态、结果提交载荷和目录交换进度。`RUNNING` 使用 Redis 租约，租约校验和事件写入在同一 Lua 脚本中完成。运行中失去租约的执行者无权交换目录。

执行者在 `delivery:{appId}` PG advisory lock 内校验租约，并在同一 PG 事务中保存候选载荷与 `COMMITTING` 状态。事务提交后，PG 持久状态决定该任务的目录交付权。Redis 租约过期时，仍由同一任务在交付锁下续作，并用同一 `taskId` 重取用于写终态事件的 Redis 租约。Java 重启时，从已保存的目录阶段及提交载荷继续交付或恢复。备份恢复和失败候选的处理规则见 [ADR 0004](0004-python-isolated-workspace-and-build-repair-loop.md)。

重复请求复用和不同指令撞车不消耗新任务的限流配额，只有实际创建任务时才执行原有限流。旧 GET 入口也必须经过同一任务协调器，不能绕过互斥直接写正式目录。

相比「仅同步生成中状态、结束后再刷新结果」，本方案需要维护两段接口与任务流生命周期，但能同时满足多标签页实时一致和刷新续看两项需求，无需为两个场景维护两套机制。
