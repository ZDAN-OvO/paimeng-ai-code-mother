# ADR-0011：Redis 消息队列与运行中 steer

- 状态：已接受
- 日期：2026-11-15
- 取代：应用忙时直接拒绝发送、首版不支持消息队列的决定

## 背景

同一应用同时只允许一个运行，单用户也有跨应用并发上限。旧行为在应用已忙、并发已满或触发限流时直接返回 409/429，用户既不能保留普通消息，也不能在 Agent 执行中补充要求。若继续让浏览器保持一个已提交但尚未开始的 legacy SSE 请求，请求会长时间占用连接；前端也不得不先取消当前运行再重新发送。

消息队列需要同时满足以下约束：

- 普通消息按入队顺序串行执行，队列不为等待中的消息提前创建运行、消息或会话记录。
- 运行中插话只能作用于当前运行，并且必须与模型上下文和公开 UI 消息保持一致。
- 多个并发请求、取消与完成竞争时不能重复认领、重复消费或永久卡在进行中。
- Redis 不可用时不能伪造成功，也不能退化为进程内队列。
- PostgreSQL 继续作为已开始运行、消息和会话记录的权威来源；重启后不能靠 Redis 自动续跑。

## 决策

每个应用在 Redis 保存一份带版本概念的队列快照，并通过“读取当前值、在内存计算、Lua 比较旧值后再写入”的 CAS 循环完成所有修改。应用 ID 注册在独立集合中，便于恢复和周期派发；删除应用时同时清理注册项和状态。进程内的派发集合只用于避免同一实例重复调度，不承担队列事实。

队列项为：

```text
{
  id,
  clientRequestId,
  message,
  mode: normal | steer,
  status: queued | claimed | started | applied | returned | removed,
  runId: string | null
}
```

`GET /app/chat/queue` 对外只返回 `queued`、`claimed`、`returned`，并单独返回当前 `activeRun`。`started`、`applied` 和 `removed` 可以通过同 `clientRequestId` 的再次入队幂等读取，但不出现在待处理列表。

普通消息的规则如下：

1. `POST /app/chat/queue` 只校验应用所有权和队列语义，然后写入 Redis；返回时不等待模型。
2. 没有当前运行时，派发器在同一个 CAS 中认领最靠前的 `normal` 项。
3. 认领成功后，现有的 PostgreSQL 运行创建事务继续执行；事务提交后才把队列项标为 `started` 并绑定 `runId`。若数据库已按 `clientRequestId` 创建运行，则复用该运行，不重复创建。
4. 运行成功结束后解除当前运行，再派发下一条普通消息；失败或取消把队列置为暂停，直到用户调用 `/resume`。
5. 数据库并发上限、单应用部分唯一索引和应用限流仍在运行创建时生效。队列项留在 Redis 中等待重试，不会通过队列绕过这些限制。

`steer` 的规则如下：

1. 请求必须携带当前 `activeRun.runId`；当前运行不存在、已经终止或 `steerOpen` 已关闭时返回 409。
2. 插话按应用队列序号排队，每次在当前模型响应及其全部工具结束并持久化后，一次性认领当时全部待处理插话；认领后新到达的消息留给下一次模型调用。
3. 会话 user 记录和公开助手消息中的 `data-steer` part 在同一个 PostgreSQL 事务中提交。part ID 固定为 `steer:<clientRequestId>`，数据为 `{ text, clientRequestId }`。
4. 只在数据库事务成功后把 Redis 项标记为 `applied`；事务失败时保留认领项供恢复核对，不能只显示到前端而丢失模型或审计记录。
5. 正常完成前，通过 CAS 检查并关闭 `steerOpen`；仍有待处理插话时继续执行。所有终态写入前再强制关闭收件箱，失败或取消时保留未生效插话，保证终态后不再接受新插话。无法关闭时不提交数据库终态，由派发器重试收尾；不继续模型调用。
6. 运行结束时仍未消费的 steer 改为 `returned` 并保留在 Redis，不写消息或会话记录，也不自动带入下一轮。用户可以移除或恢复为草稿。

## 幂等与重启

应用内 `clientRequestId` 是统一幂等键。`message`、`mode` 和目标 `runId` 完全一致时返回原队列项；任一字段不同返回 409。CAS 让并发的相同请求收敛到同一项，也让“关闭 steer 收件箱”和“接受最后一条 steer”只有一方成功。

后端仍是单实例部署，进程内存不保存可恢复的运行，见 [ADR-0005](adr/0005-single-instance-no-resume.md)。启动时先将遗留运行按数据库收尾为失败，再按稳定 `clientRequestId` 核对已有运行和已消费插话，校正已提交但尚未从 Redis 标记的项，最后暂停全部队列并启动派发器。未开始的普通项保持 `queued`，未消费插话转为 `returned`。这些步骤在接受 HTTP 请求前完成，不自动继续模型调用，避免重放文件副作用和重复计费。

每个应用最多保留 100 条待处理或未生效消息，整份队列状态上限为 1 MiB。超过上限时拒绝新增，已接受的消息和幂等记录不被淘汰；同一请求的重试不消耗新名额。成功、已生效和移除记录随应用删除时清理，用于保持应用生命周期内的幂等性。

公开消息与会话记录继续分离，见 [ADR-0009](adr/0009-separate-ui-messages-from-session-entries.md)。steer 的双写必须在同一事务中完成，因此不把任一写入提前到“前端已显示”作为成功条件。

## 运行流

`POST /app/run/stream` 只订阅已有运行并返回官方 AI SDK UI Message Stream。连接断开只移除订阅；取消必须显式调用 `/app/run/cancel`。`POST /app/chat/gen/code` 保留为兼容入口，但仍把消息交给同一个普通队列并在运行开始后返回 SSE；新客户端使用队列接口加运行流，不依靠挂起的 legacy SSE 请求排队。

## 后果

- 用户可以连续提交普通消息，并在当前运行中通过 steer 调整方向；应用忙不再造成输入丢失。
- Redis 从辅助设施变成消息排队的关键路径。Redis 不可用时应返回 503 或暂停派发，不能回退为进程内状态。
- 队列项需要稳定的 `clientRequestId`、明确的终态和清理策略；删除应用时也必须清理 Redis 注册项，否则会留下孤儿状态。
- 普通消息只在实际开始后拥有运行历史，符合“队列内容不是对话历史”的用户语义。
- 失败和取消默认暂停，可能需要用户明确继续；这是用一次操作换取不会在异常后自动连续触发模型和文件副作用。
- 全部待处理插话一起加入下一次请求，可能触及上下文预算；超限时沿用现有失败策略，不自动摘要，也不重置运行预算。
