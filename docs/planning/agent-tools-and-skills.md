**Todo 管进度，Plan 管实施方案与审批，Version 管代码状态。**
三者都需要，但不能混成一套状态。
已认可的 Loop 保持不变，保存在 agent-loop.html。
本页仍是规划草案，不替代 architecture.md 与已接受的 ADR。

## A Todo 和 Plan：都做，不再删减

上一版把任务清单误当成任务平台，把计划模式降成普通提问。
这两处判断撤回；功能纳入本轮规划。

| 概念      | 用户能看到什么                  | 不能混淆什么                     |
| --------- | ------------------------------- | -------------------------------- |
| Todo      | 本轮任务项、当前步骤、完成状态  | 勾完任务不能代替验证             |
| Plan      | 方案、范围、实施步骤与验收办法  | 不是简单问答，也不是 Todo 的别名 |
| Plan 审阅 | 批准、要求修改、拒绝            | 模型不能批准自己提交的方案       |
| 执行进度  | 实施时更新 Todo，失败时如实显示 | 等待审批不等于工作已经完成       |

建议对多步骤工作展示 Todo。
用户要求先规划时进入 Plan；重大范围变更也先提交方案。
普通小改动可以直接实施，不强制所有请求进入 Plan。

```flow
提出需求 -> {需要先规划?}
{需要先规划?} -> 进入 Plan: 是
{需要先规划?} -> 执行并更新 Todo: 否
进入 Plan -> 只读分析
只读分析 -> 提交计划
提交计划 -> {用户决定?}
{用户决定?} -> 执行并更新 Todo: 批准
{用户决定?} -> 只读分析: 要求修改
{用户决定?} -> 停止本次实施: 拒绝
执行并更新 Todo -> 验证与完成判定
```

这是 Paimeng 的建议流程，不是 v0 内部实现图。
Plan 期间允许读文件、搜索与读取 Skill。
宿主程序禁止项目写入、通用 Shell、发布与 Skill 落盘。
批准后恢复同一个主 Agent，不新增 Planner Agent。
方案变更使旧批准失效，必须审阅更新后的计划。

## B MVP 工具：补齐八项文件与项目操作

**Read、Write、Edit、Glob、Grep、Move、Delete、Bash 全部纳入 MVP。**
这是待实现的工具清单，不表示产品已经具备这些能力。
下表对应 Paimeng 的建议接口，不声称复刻 v0 内部 schema。

| 工具   | 建议接口    | 职责与限制                                         |
| ------ | ----------- | -------------------------------------------------- |
| Read   | read_file   | 分段读取文件；限制大小，拦截秘密内容               |
| Write  | write_file  | 创建或覆盖文件；覆盖前读取并校验当前修订           |
| Edit   | edit_file   | 精确替换；拒绝过期内容与不唯一匹配                 |
| Glob   | glob_files  | 按路径模式查找文件；限制范围与结果数量             |
| Grep   | grep_files  | 搜索文件内容；返回路径、行号与片段                 |
| Move   | move_file   | 移动、重命名或复制文件及目录；操作类型显式指定     |
| Delete | delete_file | 删除文件或目录；递归删除必须显式声明               |
| Bash   | run_command | 安装、构建、测试与本地 Git 命令；仅在 Sandbox 执行 |

八项工具在 M2 生成阶段一起交付。
目录枚举仍可保留 list_files，但不能替代 Glob 与 Grep。
Move 与 Delete 提供专用入口，不再仅靠 Bash 间接完成。

所有路径限定在当前 Chat 的 Workspace。
源路径、目标路径与符号链接解析都必须检查，不能越界。
Move 默认拒绝覆盖已有目标；覆盖策略必须显式指定。
Delete 执行前核对目标及预期修订，不允许隐式删除整个 Workspace。
写入、移动、复制、删除均使受影响的验证证据失效。

Plan 模式禁用 Write、Edit、Move、Delete 与通用 Bash。
专用工具不是安全沙箱；Bash 也必须遵守相同的权限边界。
Bash 具备本地 Git 能力，不等于授权远端推送或合并。
MVP 不接入 GitHub 同步；后续评估范围见 G 节。

其他工具继续保留：

| 工具                        | 职责                   | 关键限制                                      |
| --------------------------- | ---------------------- | --------------------------------------------- |
| update_todos                | 创建和更新本轮任务项   | pending、in_progress、completed；不能假报完成 |
| enter_plan_mode             | 进入只读规划模式       | 宿主程序切换允许的工具集合                    |
| exit_plan_mode              | 提交方案，等待用户审阅 | 不是自动获批或直接开工                        |
| ask_user                    | 澄清关键歧义           | 回答问题不代表批准实施方案                    |
| inspect_preview             | 查询预览就绪状态和错误 | 不承担真实浏览器操作                          |
| verify_project              | 对当前修订执行规定检查 | 检查集合不由模型随意削弱                      |
| complete_task               | 核对本轮结果与真实证据 | 不通过则返回缺失项，不自动发布                |
| load_skill、read_skill_file | 按需读取正文与参考文件 | 加载知识不扩大权限                            |
| create_skill                | 校验并创建 User skill  | 不覆盖同名技能；脚本执行要求信任              |
| fetch_url、search_web       | 网页正文抓取与联网搜索 | 校验网络目标，密钥留在宿主环境                |

Todo 与 Plan 可以保存在 Message 的结构化 parts 中。
宿主程序保存当前状态并推送 UI，不必建立任务管理平台。
执行失败或取消时保留真实状态，不把全部任务强行勾完。
已完成的 Todo 不能绕过 complete_task 的检查。

TodoManager 的精确参数未在本轮公开资料中核实。
已核实的 v0 计划出口是 agent-action：exit_plan_mode。
入口工具名与内部编排，不能仅凭名字断言。

## C 验证、完成、审批是三种不同的门

| 门             | 谁提供结果           | 证明什么                     |
| -------------- | -------------------- | ---------------------------- |
| 计划审批       | 用户                 | 允许实施这个方案             |
| verify_project | 实际检查程序         | 当前源码修订通过了哪些检查   |
| complete_task  | 宿主保存的证据与规则 | 是否满足该轮可检查的完成要求 |

证据绑定源码修订；后续改动使相关证据失效。
模型自述或 Todo 全部完成，不能替代真实检查结果。
HTTP 200 不能证明按钮工作，也不能证明视觉质量。
自然语言目标仍需 Agent 核对，用户仍能继续验收。

审批是权限状态，不要求进程一直挂着。
审批记录可持久化，但不承诺进程重启后自动续跑。
无 durable execution 的既定约束保持不变。
预算耗尽时保存工作，标记未完成，不绕过审批或检查。

## D 第一批 Skill：保留明确职责

| Skill              | 何时加载               | 负责什么                                 |
| ------------------ | ---------------------- | ---------------------------------------- |
| frontend-design    | 新建界面或重做视觉     | 视觉方向、排版、tokens、响应式与交互状态 |
| nextjs             | 新建或修改项目逻辑     | 路由、组件边界、服务端逻辑与框架约束     |
| shadcn             | 选择或组合组件         | 组件范式、主题、表单、弹窗与无障碍       |
| debug-and-verify   | 诊断错误或准备完成     | 诊断顺序、修复策略与证据解释             |
| skill-creator      | 用户要制作自己的 Skill | 描述、正文、references 与脚本规范        |
| browser-validation | 需要真实 UI 自动验证   | 观察页面、操作交互与检查响应式           |

前五个是起始集合；第六个仍依赖浏览器范围决定。
Todo 和 Plan 是核心工具与产品状态，不是两个额外 Skill。
进入 Plan 后，仍按实际任务加载相关 Skill。

M2 建议先提供最小技能加载与前四个 Skill。
M4 交付导入、信任、管理与 skill-creator。
这个交付顺序仍是草案，不代表里程碑已正式修改。

### MVP 之后：AI 与 Agent Skill，明确要做

以下技能列入 MVP 后的迭代，不是可有可无的候选项。
具体交付批次与兼容版本范围，在对应迭代再细化。

| Skill        | 后续交付目标                                 | 与 MVP 的关系                                    |
| ------------ | -------------------------------------------- | ------------------------------------------------ |
| ai-sdk       | 帮用户生成流式输出、工具调用与结构化输出功能 | 不因为 Paimeng 自身使用 AI SDK 就默认加载        |
| ai-sdk-4/5/6 | 维护不同主版本的用法与迁移参考               | 先识别目标项目依赖，不能混用不同版本 API         |
| eve          | 帮用户构建持久化、工具型、多渠道 Agent       | 目标项目能力，不是改造 Paimeng 主运行时          |
| workflow     | 帮用户构建可暂停、恢复、重试的工作流         | 不撤回 Paimeng 自身不做 durable execution 的决定 |
| chat-sdk     | 帮用户构建多平台聊天机器人                   | 平台授权与凭据须由相应迭代明确设计               |

这些是生成项目的领域知识，不是五个新的主 Agent。
仍走同一套 description 路由与正文按需加载。
技能涉及外部服务时，不能仅凭加载正文就承诺集成已可用。
eve 的具体依赖与技能规范在后续实现前核实。
本轮只确定路线，不声称这些技能已经存在。

## E 技能加载与权限保持分离

默认全量披露 name 与 description，不限制技能数量。
主 Agent 自己路由，按需加载正文与相关参考文件。
正文作为工具结果追加，不反复重写历史消息。

内置与用户 Skill 用稳定标识区分来源，避免同名覆盖。
跨轮修改重新读取真实文件，不只相信上一轮总结。
脚本只在 Sandbox 内执行；Trust 不扩大网络与宿主权限。

受控脚本入口检查信任状态，但不能把 Trust 当成代码来源隔离。
通用 Shell 仍有广泛能力，这是同 Sandbox 模型的剩余风险。
安全边界必须靠 Sandbox 与工具执行器，不靠 Skill 自律。
系统指令始终保留最低质量要求与安全规则。

## F 版本管理：MVP 维持原决策

**版本继续采用源码树 Snapshot，不在本轮对齐 v0。**
以现有 architecture.md 与 ADR 0006 为准，不替换已接受的结论。

| 项目     | MVP 规则                                       |
| -------- | ---------------------------------------------- |
| 记录时机 | 每条助手消息结束后创建 Version                 |
| 存储     | 源码树 Snapshot 保存在宿主机                   |
| 排除内容 | node_modules、.next、.git                      |
| diff     | 比对两棵源码树，输出文件级新增、删除与修改     |
| 回滚     | 把旧 Snapshot 写回 Workspace，并追加新 Version |
| 历史     | 保持线性，不删除或改写已有 Version             |
| Git      | 不以 Git commit 作为 Version 的存储机制        |

撤回上一版「有代码变更才产生 Version」的 MVP 调整。
Todo、计划与纯文字助手消息不另设免生成版本的例外。
版本产生不等于检查通过；完成判定仍依赖真实证据。

本次只修正规划草案，既有架构与 ADR 无需改写。
对齐 v0 的触发条件、历史体验与 API 模型，留待后续迭代评估。
这不是已经承诺的后续交付，也不是当前实现的前置条件。
