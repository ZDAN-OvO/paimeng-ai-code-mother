**你的核心判断成立：ToolLoop 本身就能承载开发反馈循环。**
Skills、浏览器和验证器不必各自是一个 Agent。
这些回答支持这套设计，但不能证明 v0 内部就是这样实现。

## A 哪些是证据，哪些不是？

材料来源是你贴出的 v0 Agent 七轮回答。
本页没有取得 v0 内部实现或运行追踪。

| 回答       | 可以得到什么                      | 不能据此确认什么                         |
| ---------- | --------------------------------- | ---------------------------------------- |
| Q1–Q2      | 通用前端性能与设计原则            | v0 生成代码为何更快、更好                |
| Q3         | 一套合理的开发 Agent 分层         | v0 实际用了哪些提示词与训练方法          |
| Q4、Q6、Q7 | 主 Agent 配合工具与反馈的可行模型 | 单 Agent、状态机或多 Agent 的真实拓扑    |
| Q5         | 当前会话能力的自述清单            | 完整清单、精确数量、工具是否实际执行成功 |

尤其要区分：**网页运行快，不等于 Agent 生成快。**
CDN、图片压缩与代码拆分主要解释前者。
要解释生成速度，需要观察模型耗时、工具耗时与安装耗时。
预热模板和依赖复用是我们的候选优化，不是已证实的 v0 秘诀。

## B ToolLoop 与开发反馈循环，不是两个互斥架构

ToolLoop 是执行机制：模型调用工具，工具结果返回模型。
开发反馈循环是行为：观察真实结果，并据此修复代码。

```flow
用户需求 -> 主 Agent: 理解目标
主 Agent -> 加载 Skill: 需要领域规范
加载 Skill -> 主 Agent: 返回正文与参考入口
主 Agent -> 沙箱工具: 读取或修改项目
沙箱工具 -> 主 Agent: 返回真实文件与执行结果
主 Agent -> 验证工具: 检查当前代码
验证工具 -> {检查通过?}: 返回结果
{检查通过?} -> 主 Agent: 否，带回错误
{检查通过?} -> 完成判定工具: 是，核对本轮目标
完成判定工具 -> {本轮目标满足?}: 返回判定结果
{本轮目标满足?} -> 主 Agent: 否，带回缺失项
{本轮目标满足?} -> 保存并回复: 是
```

上图是 **Paimeng 的建议设计**，不是 v0 内部架构图。
矩形表示工具或动作，菱形表示依据结果选择分支。

验证工具检查代码；完成判定工具核对本轮目标与完成证据。
两种工具都不必是独立 Agent，也不必调用额外模型。
同一个主 Agent 可以完成分析、实现、检查与修复。
Few-shot 提供行为示例；它不负责实际执行或观察环境。

## C 系统必须区分「停了」和「做好了」

| 状态               | 含义             | 应有的产品行为         |
| ------------------ | ---------------- | ---------------------- |
| 模型不再调用工具   | 模型认为可以结束 | 检查本轮完成证据       |
| 到达步数或时间限制 | 资源预算耗尽     | 标记未完成，保留现场   |
| 检查失败           | 当前代码未过要求 | 在剩余预算内继续修复   |
| 检查通过           | 指定检查通过     | 再核对是否覆盖用户要求 |
| 用户取消或运行异常 | 本轮中断         | 如实说明，不显示成功   |

**最大步数是熔断，不是验收。**
**构建通过是必要证据之一，不是 UI 质量证明。**

建议由宿主程序保存检查结果，绑定当前源码修订。
修改代码后，受影响的旧检查结果不能继续充当完成证据。
模型说「已测试」不能替代实际工具结果。

检查未齐全时，宿主程序应阻止成功状态。
剩余预算允许时，把缺失项送回同一个主 Agent。
这不要求 durable execution，也不要求多 Agent。

## D 美感不能只靠「安装了 shadcn」

必须分开讨论两个界面：Paimeng 工作台与用户生成应用。
工作台使用默认 shadcn，不代表生成应用只能用默认外观。

| 载体       | 应负责什么                         | 不应承担什么           |
| ---------- | ---------------------------------- | ---------------------- |
| 系统指令   | 安全边界、完成条件、最低质量要求   | 塞入所有领域知识       |
| 设计 Skill | 层级、排版、间距、响应式与交互规范 | 为每个项目套同一种页面 |
| 起始模板   | 可运行项目、依赖与组件基础         | 决定每个产品的视觉方向 |
| 项目文件   | 已有主题、组件与用户修改           | 每轮全部重新生成       |
| 浏览器反馈 | 真实页面、溢出、点击行为与截图     | 自动保证审美优秀       |

推荐先确定符合需求的视觉方向，再落成项目级 tokens。
后续修改读取并延续 tokens，而不是每轮重新挑颜色和字号。
设计 Skill 可以按需加载；最低质量底线不能依赖路由碰巧选中。

## E 现有架构缺的不是另一层编排

现有文档已选定 ToolLoop、模型自路由与按需加载。
这些回答不足以推翻该选择。

| 已有约定                         | 需要澄清的缺口                     |
| -------------------------------- | ---------------------------------- |
| D3：ToolLoop 承载循环            | 哪些真实检查结果允许本轮成功       |
| D12：生成模型选择 Skill          | 通用质量底线与领域 Skill 的边界    |
| 验收 3：多文件项目通过构建       | 检查失败如何返回同一个 Agent       |
| 验收 12：抓取网页正文与联网搜索  | 这不等于操作生成页面的真实浏览器   |
| 预览不提供 logs 与 terminal 面板 | Agent 仍需读取进程错误与浏览器错误 |

**HTTP 抓取无法证明按钮可以点击，也看不到实际布局。**
如果要兑现 UI 自动验证反馈循环，需要真实浏览器能力。
这是现有范围的澄清候选，尚未替用户修改验收契约。

## F 最小可行方案：一个 Agent，两个硬边界

知识边界：Skill 提供知识，不提升权限。
用户导入 Skill 不能突破宿主程序的工具权限与沙箱限制。
模型密钥留在宿主环境，用户代码只在沙箱执行。

完成边界：Agent 提出完成，宿主程序判断证据是否足够。
检查与修复有预算；失败必须明确呈现。
发布仍是受控操作，不因模型结束回答而自动发生。

建议先用少量代表任务检验这条链：

- 首次生成：完整项目、构建通过、预览可访问。
- 多轮修改：目标内容改变，已有功能仍可用。
- 故障恢复：引入可修复错误，读取失败并修复。
- 预算耗尽：保留代码，明确显示未完成。
- UI 验证：实际操作主要交互，检查窄屏布局。

无需从 v0 的长技能清单开始复制。
先证明主循环会使用真实反馈，再扩展领域能力。
