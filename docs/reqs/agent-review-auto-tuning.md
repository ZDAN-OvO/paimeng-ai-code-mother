## Requirement

plan 和 todo 是工具，交给主 agent 决定是否调用，不做成强制工作流；code/completion review 做成 subagent，review 前需要有 CI；系统提示词离线自动调优，夜间自动拿数据集跑测试，对比结果，提 PR，测试集合需要持续维护，保证不过时得出错误结论。

补充确认：

- 本轮产出是设计文档，不写代码：rung 1 到 rung 5 都写成 `architecture.md`、ADR、`mvp.md`、`GLOSSARY.md` 里的设计，实现另起任务。

- 调优对象取宽口径：主 agent、code review agent、completion review agent 的提示词，主 agent 判断「是否 review」的提示词，打回上限与模型选择。
- 只有 CI，没有 CD：发布仍由用户触发。确定性检查每轮必跑，没有通过记录的修订不能标成成功。
- 阶梯中间层、评测方法、防跑偏手段、前提与目标线全部保留，见下文 Ladder 与 Deeper。

## Deeper

- Premise: holds
- Kept: S1 契约先定 review agent 能拿到哪些证据，再定怎么审；检查信号弱、需求没说清，加 agent 解决不了
- Kept: S2 主 agent 与 review agent 用不同家族模型（deepseek-v4.1-flash、glm-5.3-flash），rung 4 加同家族对照
- Kept: S3 主 agent 判断是否 review、做哪种 review，不写死流程；小改动只跑确定性检查，大改动在检查后调用 code review（可多次、可局部），交付前才调用 completion review；review agent 包成工具供主 agent 调用
- Kept: S3a 宿主守底线：确定性检查每轮必跑，没有通过记录的修订不能标成成功
- Kept: S3b 漏审率作为指标：用例预埋需要 review 的大改动，统计该审没审的比例，用来调主 agent 的判断提示词
- Kept: S4 用例构造时预埋已知缺陷，判定基准事先已知，不靠 LLM 判分
- Kept: S5 一手材料是每次运行的完整记录，按「用例 × 配置 × 第几次」存放；`archive/` 旧测评集只作参考，重新写
- Kept: S6 指标用混淆矩阵计算，用例集包含干净项目以计算误打回率
- Kept: S7 输出不稳定时用 pass^k，先取 k = 3
- Kept: S8 A/B 用配对设计与 McNemar 检验
- Kept: S9 保留集冻结，只在决定能否上线时使用，用过几次就换；每份先 20 条起
- Kept: S10 反思式提示词优化（GEPA、DSPy 一类），先手工跑两三轮再决定是否接框架
- Kept: S11 每轮调优设 token 与候选数熔断，超限停下报告，不自动加钱
- Kept: S12 每次大调优后人工抽检 10 条 review 结论，用 Cohen's κ 校准
- Kept: S13 交付后返工率是真实指标，只做人工观察，不进自动循环
- Kept: S14 只用 flash 模型，保留集上拦截率 ≥ 90%、误打回率 ≤ 5%；离线调优循环在预算内无人值守跑一晚，产出带证据的 PR；没达到就如实报告差距
- Dropped: 上线后自动调优，与 ADR 0007（单用户、本地优先）冲突，也没有汇总的线上数据
- Dropped: review 由宿主固定流程触发（原 S3），用户认为每次小改动都跑两个 review 成本太高，且 code review 与 completion review 不是一对一关系
